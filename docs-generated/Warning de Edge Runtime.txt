# 🐛 Problema: Warning de Edge Runtime com biblioteca `jose` no Next.js 15 + Render

## 📌 Contexto do Projeto
- **Framework**: Next.js 15.5.18

- **Biblioteca problemática**: `jose` (usada em `src/backend/lib/jwt.ts` e `src/backend/middleware.ts`)

---

---

## 🔍 O que está acontecendo?

O arquivo `middleware.ts` do Next.js roda por padrão no **Edge Runtime**, que tem limitações de APIs disponíveis. A biblioteca `jose`, ao ser importada, está usando APIs do Node.js (`CompressionStream` e `DecompressionStream`) que **não são suportadas no Edge**.

Isso gera warnings durante o build. Embora o build possa concluir com sucesso, pode causar falhas em runtime no middleware.

---

## ✅ Soluções Sugeridas (escolha uma)

### 🔹 Opção 1: Forçar runtime Node.js no middleware (Recomendado)

No arquivo `src/backend/middleware.ts`, adicione a configuração de runtime:

```typescript
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(request: NextRequest) {
  // sua lógica atual...
  return NextResponse.next();
}

export const config = {
  matcher: ['/caminhos/:path*'], // ajuste conforme seus paths
  runtime: 'nodejs', // ← Força uso do Node.js runtime (Next.js 15.2+)
};
```

> ✅ Vantagem: Resolve o problema sem refatorar a lógica do `jose`.  
> ⚠️ Observação: O middleware perderá os benefícios de latência do Edge, mas ganha compatibilidade total com Node.js.

---

### 🔹 Opção 2: Usar imports compatíveis com Edge Runtime da biblioteca `jose`

Substitua imports genéricos por imports específicos da versão Web:

```typescript
// ❌ Evite:
import { jwtVerify, SignJWT } from 'jose';

// ✅ Prefira:
import { jwtVerify } from 'jose/jwt/verify';
import { SignJWT } from 'jose/jwt/sign';
import { importPKCS8, importSPKI } from 'jose/key/import';
```

E certifique-se de que a versão do `jose` está atualizada:
```bash
npm install jose@latest
```

> ✅ Vantagem: Mantém o middleware no Edge Runtime.  
> ⚠️ Desvantagem: Pode exigir ajustes na forma como as chaves e tokens são manipulados.

---

### 🔹 Opção 3: Mover validação de JWT para Server Actions ou API Routes

Se o middleware não precisa validar tokens, mova essa lógica para locais que rodam no Node.js por padrão:

```typescript
// app/api/auth/verify/route.ts (API Route)
import { jwtVerify } from 'jose';

export async function POST(request: Request) {
  const { token } = await request.json();
  const verified = await jwtVerify(token, new TextEncoder().encode(process.env.JWT_SECRET));
  return Response.json({ valid: true });
}
```

E no middleware, faça apenas uma chamada HTTP para validar:
```typescript
// middleware.ts
export async function middleware(request: NextRequest) {
  const token = request.cookies.get('token')?.value;
  
  if (token) {
    const res = await fetch(`${process.env.NEXT_PUBLIC_BASE_URL}/api/auth/verify`, {
      method: 'POST',
      body: JSON.stringify({ token }),
    });
    if (!res.ok) return NextResponse.redirect(new URL('/login', request.url));
  }
  
  return NextResponse.next();
}
```

> ✅ Vantagem: Separação clara de responsabilidades e compatibilidade garantida.  
> ⚠️ Desvantagem: Adiciona uma chamada HTTP extra (pode ser mitigada com cache).
